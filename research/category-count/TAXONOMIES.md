# Category-count experiment: taxonomies and exact mapping rules

Schema `diaporia.semantic-category.v1.0.0`, projection `category-projection-1.0.0`.
Code: `src/intent/hybrid/category/CategoryTaxonomy.ts` (taxonomy tables, `fineOf`, `groupOf`) and
`src/intent/hybrid/category/CategoryIntent.ts` (Zod schemas, validator, projection). Prompts and JSON schemas are generated by
`build-prompts.mts` from one template (`PROMPT_TEMPLATE.txt`) and one example set (`examples.k7.json`); hashes in `MANIFEST.json`.

## 1. What is identical in every arm

- The atomic unit: `span` (verbatim), `facet`, `status`, `attribute`, `operator`, `value`, `unit`, `target`, `component`,
  `resolution`, `en`, `brand_latin`, `brand_latin_alternatives`. Same enums, same lengths, same nullability.
- Document fields: `taxonomy`, `language`, `item_kind`, `units`, `unresolved`. `unresolved` is a separate list in every arm
  and is never a category.
- The prompt text apart from the taxonomy block (and, in K3F, one line describing the optional sub-type).
- The four worked examples: the same requests and the same atomic units; only the category label is re-derived per arm.
- Model `claude-haiku-5-5`, one request per call, no tools except structured output, same system prompt, same CLI flags,
  same thinking setting, structured output with the arm's JSON schema (`schemas/<ARM>.json`, from the same Zod factory).
- Validation (`validateDocument`), projection (`projectToV11`), the downstream typed adapter v0.2, the engine, evidence,
  gates and payment code.

## 2. The seven fine categories and the nested chain

| # | Fine category | Meaning |
|---|---|---|
| 1 | IDENTITY | product type, brand, model/variant words, host of an accessory, kind markers |
| 2 | REQUIREMENT | a feature or measurable property the item must have |
| 3 | EXCLUSION | a feature, property, variant, model or kind the user does not want |
| 4 | RELATION | fit / works with, capacity for a load or user, bundle contents |
| 5 | PURCHASE | price limit, condition, quantity, delivery, seller |
| 6 | PREFERENCE | nice-to-have |
| 7 | CONTEXT | background only |

Each level splits exactly one category of the level below:

| Arm | Categories (fine members) |
|---|---|
| K3 | IDENTITY (1) · BINDING (2,3,4,5) · NON_BINDING (6,7) |
| K4 | IDENTITY (1) · PRODUCT_CONDITION (2,3,4) · PURCHASE (5) · NON_BINDING (6,7) |
| K5 | IDENTITY (1) · PRODUCT_CONDITION (2,3,4) · PURCHASE (5) · PREFERENCE (6) · CONTEXT (7) |
| K6 | IDENTITY (1) · PRODUCT_CONDITION (2,3) · RELATION (4) · PURCHASE (5) · PREFERENCE (6) · CONTEXT (7) |
| K7 | IDENTITY · REQUIREMENT · EXCLUSION · RELATION · PURCHASE · PREFERENCE · CONTEXT |
| K3F | K3 core (required) + optional `subtype` ∈ the 7 fine categories (null allowed) |

The split order (binding/non-binding first, then product vs purchase, then preference vs context, then relation, then
exclusion) is a design choice. Another order would give different K4–K6 groupings; this is a stated limitation.

## 3. Exact mapping rules

### 3.1 Fine category implied by the atomic fields (`fineOf(facet, status)`)

Evaluated top to bottom:

1. `status = context` → CONTEXT if facet is `background` or a relation facet; otherwise **no meaning** (conflict).
2. facet `background` with any other status → **no meaning** (conflict).
3. `status = preferred` → PREFERENCE.
4. purchase facet (`budget`, `condition`, `quantity`, `delivery`, `seller`) → PURCHASE.
5. `status = forbidden` → EXCLUSION.
6. identity facet (`product_type`, `brand`, `model`, `host`, `kind_marker`) → IDENTITY.
7. relation facet (`compatibility`, `suitability`, `includes`) → RELATION.
8. otherwise (`feature`, `measure`, mandatory) → REQUIREMENT.

### 3.2 Category check (`classify`)

A unit is consistent iff `category == groupOf(arm, fineOf(facet, status))` and, in K3F, `subtype` is null or equals the
fine category. An inconsistent unit is a **classification error**: it is not executed, it is recorded as an ambiguity in
the projected document, and the parser's own reading of that span stands (fail closed, no new gate).

### 3.3 Projection into `diaporia.semantic-intent.v1.1` (`projectToV11`)

| Fine category | v1.1 field |
|---|---|
| IDENTITY | `item.product_type` (first `product_type`; `en` = attribute), `item.brand`, `item.model`, `item.host` (first of each); a second one becomes an ambiguity; `kind_marker` informs nothing beyond `item_kind` |
| IDENTITY brand in non-Latin script with `brand_latin` | `brand_proposal {span, brand_latin, brand_latin_alternatives}` (verified downstream by the v0.2 planner check) |
| REQUIREMENT | constraint `role = mandatory` |
| EXCLUSION | constraint `role = exclusion` |
| RELATION | constraint `role = compatibility` |
| PREFERENCE | constraint `role = optional` |
| CONTEXT | constraint `role = context` |
| PURCHASE budget (mandatory) | `budget {span}` (informational: money always comes from the parser) |
| PURCHASE condition new/used/refurbished/any (mandatory) | `condition {value, span}` |
| other PURCHASE (quantity, delivery, seller, forbidden condition) | constraint `role = mandatory` (or `exclusion`), so it stays an open condition, never approximated |

Constraint fields: `numeric = {op, value, unit}` only when the operator is one of `>= <= > < =` and the value is a number;
`subject` = target (`item→product`, `purchase→other`); `component` copied. Units with identical role, span and numeric
value are emitted once. `unresolved` entries and `resolution = ambiguous` units are copied to `ambiguities`.
`item.kind = item_kind`; `language ja → other`; `confidence = medium` (unused downstream).

## 4. Validator measures (same code for every arm)

- schema validity (Zod), non-verbatim spans, classification conflicts,
- **coverage**: content tokens of the request (letters/digits runs minus a fixed filler list) not inside any unit or
  unresolved span,
- duplicated mandatory units (overlapping spans, same fine category and attribute),
- unresolved entries and ambiguous units.
