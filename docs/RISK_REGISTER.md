# Remaining risk register (2026-11-10, before Scenario I run 3)

Each risk is classified once:

- **Run 3 blocker**: Scenario I run 3 (local, MOCK, one server process) must not start until it is fixed.
- **Phase C blocker**: must be resolved or verified before any PayPal Sandbox step (C1/C2/C3), each of which still needs its own owner approval.
- **Production-only limitation**: acceptable for local MOCK and the single-process Sandbox demo, but must be resolved before any real deployment.

"Unverified" means nobody has checked it against PayPal's own documentation or a Sandbox run. Official PayPal developer pages are not reachable from the cloud environment.

| # | Risk | Classification | Why |
|---|---|---|---|
| R1 | **Multi-process reservations.** With two server processes on one database, a cancel can land between the owner-page claim transaction and the reservation in `startPayment`. The bound mandate then keeps a reservation for a dead checkout. Found in the DF-4 review (F2), by reasoning; not reproduced. | Production-only limitation | The reservation stays bound to the dead checkout and cannot move to another one: it is a leak, not an escalation. Run 3 and the Phase C demo each run one DIAPORIA process per database. Before production: put claim and reservation in one transaction, or sweep stranded reservations. |
| R2 | **PayPal idempotency retention and late reconciliation.** DIAPORIA replays create-order and capture with the same `PayPal-Request-Id` to recover from timeouts. PayPal honours a repeated id only for a limited window; the window is **unverified**. A create replay after the window can create a **second order**. A capture replay after the window could get a different answer. It is also unverified whether PayPal refuses a second capture of the same order. | **Phase C blocker** | Run 3 is MOCK, whose idempotency map never expires, so it cannot show this. In Sandbox, **this document does not claim that two orders can never be created.** Before C2: verify the retention window and the replay errors (409 in progress, 422 already captured) from PayPal's documentation or a dedicated Sandbox probe, then bound replay age so that an older replay stays UNKNOWN for manual review. Since 2026-11-10 a 4xx on a capture *replay* already stays UNKNOWN with the reservation kept, never FAILED. WP-3 (IR-11) bounds the create replay: reconcile never replays create-order past the checkout's expiry or when the first attempt (`create_requested_at`, else `created_at`) is older than 5 h (`SAFE_CREATE_REPLAY_WINDOW_MS`; the documented default retention is 6 h, behaviour unverified, IR-18). Such a checkout stays UNKNOWN with its reservation for manual review (`RECOVER_CREATE_SKIPPED`). The capture replay is not changed by WP-3. |
| R3 | **Expired UNKNOWN checkout recovery.** Startup recovery is read-only: it adopts captures it finds, but does not replay a create or close anything. An expired UNKNOWN checkout waits for an owner `reconcile`. If a capture was requested and the provider shows none yet, the checkout stays UNKNOWN with the reservation held. It closes only on provider evidence, a VOIDED order with no capture, which arrives at a PayPal-defined time (unverified). A CAPTURE_PENDING row with no capture id (process stopped mid-capture) is recovered only by an owner reconcile after 5 minutes. A stall of over 5 minutes in a live process could let that reconcile replay a live capture. It uses the same request id, so it is safe only through R2. | Production-only limitation | It fails safe: no new capture past expiry, no blind retry, no release without evidence. The cost is held authority and manual work. Run 3 requires COMPLETED for every host, so any UNKNOWN is already a reported failure. Before production: a reconciliation queue with alerting, and verified PayPal void timing. |
| R4 | **Persisted ACTIVE status after effective expiry.** A mandate past `expires_at` still reads `status = 'ACTIVE'` in the database. `PurchaseMandate` reports it as EXPIRED and policy denies it (`MANDATE_EXPIRED`). Run 2's two leftover mandates show exactly this. | Production-only limitation | Every authorization path reads the derived status, so no spending is affected. The run 3 evidence builder does not read `status`. Raw database views (ops, audit exports) can mislead. Before production: sweep expired rows, or derive the status in every view. |
| R5 | **Host semantic fidelity.** In run 2 Hermes called the MOCK payment "PayPal sandbox". The server's own text said so in MOCK mode: the checkout `disclosure` ("PayPal Sandbox demonstration") and the `prepare_checkout` tool description. Fixed on 2026-11-10: both now follow the environment. `checkoutPath` still carries the enum value `PAYPAL_SANDBOX_DEMO_MERCHANT` in MOCK; it is not renamed because it is a contract value. | Not a blocker (measured) | Run 3 measures this with the separate Semantic Fidelity v1 evaluation, which never changes the 17 checks. A host that still says "Sandbox" is reported as CONTRADICTED; the enum value is a known possible source. |
| R6 | **Stricter expiry in the human step.** Since the expiry hardening, the owner authorization and the buyer approval must both finish within 15 minutes of each host's prepare. Run 2 already lost two hosts to human timing. | Not a blocker (procedure) | Nothing is captured after expiry and no authority remains. The runbook now states the window and how to record a timing failure. |
| R7 | **Same-OS-user AI host (IR-01 / SR-01, operational part).** WP-1 makes every purchase need a human step (owner key on the MOCK buyer page or PayPal's own buyer login; owner opt-in for automatic mandate use). Code cannot stop an AI host that runs as the same OS user as DIAPORIA: it can read owner keys from `.data/` or the environment and write the SQLite database directly. | **Phase C (C1) precondition** | Before C1: every AI host runs under a different OS user or in a different container from the DIAPORIA process, cannot read `.data/` (owner keys, dev credentials, Scenario I key files) and cannot write the database file. This is an operating condition, not something the code enforces; record how it was met in the C1 approval. |
| R8 | **Payment routes accept the owner key without a passkey (V22-05 / R-A-1).** Checkout authorization, owner-API mandates, the handoff and MOCK approval accept the owner key alone. Research holds already need a passkey. The independent IW-5 to IW-14 evaluators each showed it (IW-14 probe G10 on 7bd5128; IW-13 probe G10 on 51f9eb7; IW-12 probe G10 on 6b7f994; IW-11 probe G10 on fea57b7; IW-10 probe G10 on b3c0ed0; IW-9 probe G10 on 177b490; IW-8 probe G10 on e5cc4de; IW-7 probe G10 on 6ada5b0: mandate 201, prepare, MOCK approve 303, COMPLETED with one capture and no passkey). The owner key is protected at rest only by the OS-account boundary. | Production-only limitation | Binding payment routes to a passkey assertion is a new approval step, so it is the operator's decision and is not added by the development agents. It must be decided and implemented before any deployment with a real payment method. |
| R9 | **The service-isolation self-check trusts declared uids (V22-04 / H2-R1).** A copy of the service started from the AI host's own account with a fake `DIAPORIA_AI_HOST_UIDS` reports isolation as established (IW-7 probe G11 on 6ada5b0, IW-8 G11 on e5cc4de, IW-9 G11 on 177b490, IW-10 G11 on b3c0ed0, IW-11 G11 on fea57b7, IW-12 G11 on 6b7f994, IW-13 G11 on 51f9eb7 and IW-14 G11 on 7bd5128, run as root in a disposable container). The copy cannot reach the real service's gate, keys or audit trail; the documented setup (S0) is established and the misconfigurations S2/S3 are correctly refused. | Production-only limitation | Before any deployment, the check must compare the service uid with a root-owned pin instead of trusting the declared AI uids. |

**Run 3 blockers: none open** after the 2026-11-10 changes: DF-3, DF-4 and expiry capture prevention are fixed with regression tests. **Phase C blockers:** R2, in addition to the existing Phase C holds (independent C0 review, exact HTTPS host, signed C1 approval).
