# V2.1 review remediation (V21-01 … V21-04)

Scope: the HIGH findings V21-01…03 and V21-04, which must be fixed before any payment-facing release, from the
independent review of 91a0a52. Eric approved them on 2026-11-11 and chose Option A for V21-04. Everything here is a
local commit only. No provider, PayPal, Sandbox or KERNEL call was made.

## 1. Interfaces for an external runner (IW-2)

**Tools.**
- No tool was renamed and no argument was renamed.
- `resolve_research_hold` keeps its name, its PREPARE scope and its input schema: `purchaseSessionId`, `kind`,
  `requirement`, `budgetMinor`, `currency` and `userStatement`.
- Its behaviour changed. It only creates a proposal. The result is:

  ```
  { purchaseSessionId, state, proposalId: "rhp_<uuid>", status: "PENDING_OWNER_CONFIRMATION",
    ownerConfirmationUrl: "<baseUrl>/research-holds/rhp_<uuid>", expiresAt, readiness: { ready, open, ... },
    nextStep, paymentEffect: "NONE" }
  ```

- `readiness.ready` stays false. Compare stays HOLD, and both prepare paths still refuse.
- A proposal that cannot be resolved is refused with `INVALID_INPUT`, and nothing is stored. That covers a wrong
  currency, a missing amount, a key that is not open, and `CONFIRM_BUDGET` when no budget is unresolved.
- `_meta["diaporia/requiresOwnerConfirmation"] = true`.

**Vocabulary.**
- `decision.state` is unchanged: `RECOMMEND | INVESTIGATE | HOLD`. There is no new clarification state. A question is
  always a HOLD with `holdReasons`.
  - An unresolved budget gives HOLD, and its reason starts "Budget unresolved".
  - Several model years with none stated gives `identity.status: "AMBIGUOUS"`, and the HOLD reason is the resolver's
    question naming `year`.
- The purchase session state is `HOLD` whenever the decision is not RECOMMEND or a gate item is open.
- New `purchaseReadiness.open` line forms:
  - `Budget unresolved: "<text>" has no currency …`
  - `Unresolved requirement attribute:year: year 2025 is not confirmed by the listing`

**Variant strings.**
- A model year appears in `identity.variant` as `year=2025` (for example `Black / year=2025`).
- The model has no year (`model: "Drift 15"`).

## 2. Owner confirmation flow (V21-04): routes and the 10 invariants

**Routes.** These are in `src/http/researchHoldRoutes.ts`. They return 403 when payment execution is disabled.

| Route | Effect |
|---|---|
| `GET /research-holds/<rhp_id>` | Explanation and an owner-key form. No proposal content, no cookie, no state change. |
| `POST … action=review ownerKey=<key>` | Verifies the owner key, which must be the proposal's own user (another user's key gives 404). PENDING and unexpired only: a decided proposal gives 409, an expired one 410. Opens a review session for 10 minutes, or until the proposal expires if that is sooner. The session is bound to the user, the proposal and the proposal digest. Cookie: `dac_hold`, HttpOnly, SameSite=Strict, Path=/research-holds (Secure on https). The page carries a CSRF token. |
| `POST … action=confirm csrf acknowledge=yes [budget=<typed amount>]` | Requires the session cookie and its CSRF token, the explicit tick, and for `CONFIRM_BUDGET` the amount typed again, which must equal the proposal. A session for another proposal gives 403 and is not consumed. The session is single use. The gateway re-checks the digest, the open item and the session currency. It moves the proposal from PENDING to CONFIRMED (a conditional UPDATE) and appends the resolution in one transaction. |
| `POST … action=reject csrf` | Moves the proposal from PENDING to REJECTED. The gate does not change. |

All POSTs need a strict same-origin browser post (an allowed `Origin`, or `Sec-Fetch-Site: same-origin`). A request
that carries an `Authorization` header is refused.

**How each invariant is met.**

| # | Invariant | Where |
|---|---|---|
| 1 | Only an authenticated human owner confirms | The owner key is checked by `verifyOwnerKey`. A bearer token is never an owner credential, and a request with `Authorization` is refused. |
| 2 | Bound to user, session, requirement, change and currency | Proposal row and `proposalDigest()` over all of them plus the item. The review session holds the digest, and confirm re-checks it. |
| 3 | Shows the original item, the uncertainty, the change, and the agent text labelled as the agent's | `reviewBody()`: "Written by the AI assistant … not verified as your words". |
| 4 | Fresh explicit action, CSRF, expiry, single use | Tick plus typed budget, CSRF, 30-minute proposal, 10-minute session, session deleted on use, conditional status UPDATE. |
| 5 | GET never mutates | The GET branch only renders. Tested: no cookie, and the gate is unchanged. |
| 6 | The agent cannot obtain or replay credentials | The tool result is only a URL. The cookie is HttpOnly and issued only in answer to the owner-key POST. CSRF appears only on the owner-authenticated page. Replay gives 401 or 409. |
| 7 | Append-only audit; the original is kept | `RESEARCH_HOLD_PROPOSED`, `_CONFIRMED_BY_OWNER` and `_REJECTED_BY_OWNER` in the hash-chained journal. Gate items are never removed; resolutions are appended with `confirmation: "CONFIRMED_BY_OWNER"`, `actor: OWNER_SESSION:<fp>`, `proposalId` and `proposalDigest`. |
| 8 | Direct MCP resolution rejected, including fabricated `userStatement` | The tool cannot resolve. `gateReadiness` ignores any resolution that is not owner-confirmed, and `resolveGate` refuses one. |
| 9 | Both checkout paths re-check | `assertPurchaseReady` in `prepareCheckout` and `BrowserCheckoutHandoff.prepare`, unchanged. |
| 10 | Clear disclosure for contradicted must-haves and budget increases | A red warning when the item is `MUST_HAVE_CONTRADICTED`, or when the proposed budget is above the session budget or the amount in the request. |

Tests: `tests/research-v2.1-remediation-owner-confirm.test.ts` (HTTP, MCP and the human role played separately) and
`tests/research-v2.1-purchase-gate.test.ts` (gate rules). The Phase C flow in `tests/phase-c-handoff.test.ts` now
confirms through the owner page with `ownerConfirmsHold()`.

**Residuals (as of 7d1fe4f; see §4 for what changed).**
- ~~The server cannot tell the human from a process that holds the owner key and forges browser headers.~~ Closed by
  R-A (§4): confirming now needs a passkey assertion with user verification.
- ~~There is no rate limit on owner-key attempts.~~ Closed by R-B (§4).
- The proposal and session stores are in process (sessions) and in SQLite (proposals). A restart drops open review
  sessions but not proposals.

## 3. KRW budgets (decided by Eric, 2026-11-11)

Parsing a KRW budget correctly and verifying a price in KRW are separate questions (V2.1_EVAL_PROTOCOL.md §6a). A
valid KRW budget is kept as parsed and never converted. Channel3 documents no Korean market and no KRW
(PROVIDER_COMPLIANCE_REVIEW.md), so with USD-only listings a KRW session gives HOLD or INVESTIGATE
(`PRICE_NOT_IN_REQUESTED_CURRENCY`) and never claims budget compliance. A future provider that prices in KRW can reach
RECOMMEND. Tests: tests/research-iw2-p1.test.ts ("KRW policy").

**Residuals (recorded, not fixed).**
- **R-A-1.** Checkout authorization, mandates, the browser handoff and the MOCK buyer step still accept the owner key
  alone (no passkey). The owner key is no longer written anywhere the AI host can read, but a leaked owner key opens
  those pages. Next step: the same assertion on `/authorize` and `/handoff`.
- **R-A-2.** `DIAPORIA_OWNER_KEYS` still works and puts owner keys in the server's environment, readable by a
  same-user process; the server warns at startup. Research-hold confirmation needs the passkey regardless.
- **R-A-3.** The protection rests on the OS: an AI host running as root or as the owner account, or a compromised
  browser on the owner's device, defeats it. A server running as root fails closed (every directory is root-owned).
- **R-A-4.** Passkeys need a host name: use `PUBLIC_BASE_URL=http://localhost:<port>`, not 127.0.0.1.
- **N-05-1.** A descriptive word between the model and the category noun in a listing title ("K9 Home Projector")
  becomes part of the listing's model, so a request for "K9" finds nothing (fails safe: NOT_FOUND / HOLD).
- **N-07-1.** The Korean query glossary is small and only builds queries; a Korean product word outside it is dropped
  from the query, and a request with no recognisable product word makes no catalog call (no RECOMMEND).
- **N-06-1.** A model-less identity is only as authentic as the provider key; a product listed under two provider ids
  is two identities.
- **Provider.** PROVIDER_COMPLIANCE_REVIEW.md: live outputs stay private (benchmark clause); two small live smoke files
  are already on public main and need Eric's decision; commission disclosure and a retention limit are open.
