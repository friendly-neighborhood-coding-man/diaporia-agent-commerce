# DIAPORIA Agent Commerce: submission notes

This page is the reviewer's entry point. It says what DIAPORIA does, how to reproduce it, what is proven, what is simulated and what is still open. Numbers marked *seen* come from evaluation sets the builder has already looked at. They are regression evidence, not independent evidence.

## Project description (Devpost)

**DIAPORIA: bring safe purchasing to the AI assistant you already use.**

AI assistants can already find products. The risky part is everything after that. They might buy the wrong model, trust a listing that tells them what to do, call a search price the "total", or spend money the user never authorized. DIAPORIA is an MCP server that any assistant (Claude, ChatGPT, Grok, Codex, Hermes) can call. The assistant does the talking. DIAPORIA owns the facts and the money boundary.

- **Grounded research.** The user's words become structured requirements: the budget, the exact model, MUST and nice-to-have features, and unfamiliar requirements as generic propositions. Each requirement is verified from attributable evidence. A manufacturer can state a property, but a performance claim such as "quiet" or "comfortable" needs two independent expert sources. Listing text is never evidence, and text that tries to instruct the AI is flagged.
- **No silent substitution.** The exact model, variant, condition and kind (standalone, bundle or accessory) are locked. "A9" never becomes "A9 Pro". A request word that research could not interpret blocks recommendation instead of being ignored.
- **Honest outcomes.** RECOMMEND only when every MUST requirement is verified. INVESTIGATE says exactly which requirement is open and why. HOLD says what is known to be wrong. Ranking can never compensate for an unmet requirement.
- **Verified totals.** Offers are compared on fresh merchant quotes with shipping and tax, and merchant identity is checked against a registry. A search price is never shown as a checkout total. Unknown costs stay unknown, and an unsupported currency is refused, never converted.
- **Bounded spending.** The AI can prepare a checkout but cannot authorize one. The human sets a spending limit on the owner page, and the buyer approves on PayPal's page. The limit is server-enforced and atomic, and every step is in an audit trail. Only the owner, with a passkey, can settle a requirement the research could not verify. The ledger then says OWNER_ATTESTED, never VERIFIED.

**Built with:** TypeScript, Node 22 (`node:sqlite`), the official MCP TypeScript SDK (Streamable HTTP), PayPal Orders v2 (Sandbox adapter), WebAuthn-style passkey verification, Channel3 and Tavily adapters (bring your own key; off by default).

## Reproduce

```bash
git clone <repo> && cd diaporia-agent-commerce
npm ci                 # Node.js 22.13+
npm run demo:full      # unattended end-to-end demo, offline, MOCK; writes demo-output/<run>/trace.json + transcript.md + trace.sha256
npm test               # 977 automated tests (offline)
npm run typecheck
```

Measured on a fresh clone in the build container, with a warm npm cache: clone, `npm ci` and `demo:full` took 4.6 s in total. The demo itself runs in about 0.4 s and has 18 checked steps. A failed expectation exits non-zero, so a run is never shown as successful when it was not.

| Merchant fulfilment | Not claimed (`merchantPurchaseComplete: false`) | Not provided |

## Open risks (not fixed, stated plainly)

- **Payment routes accept the owner key without a passkey** (V22-05 / R-A-1). The IW-5 to IW-17 evaluators each confirmed it (IW-16 probe G10 on 71bb3aa; IW-17 on 161146e): a stolen owner key alone completes a MOCK purchase end to end. Research holds already require a passkey. Checkout authorization, owner-API mandates, the handoff and MOCK approval rely on the owner key, which is protected at rest by the OS-account boundary. Adding a passkey there is a deployment precondition. It is not done here, because a new approval step is the operator's decision.
- **The service-isolation self-check trusts declared uids** (V22-04 / H2-R1). The independent IW-5 and IW-7 to IW-17 evaluators showed it (IW-17 probe G11 on 161146e): a copy of the service run from the AI's own account with a fake AI uid reports isolation as established. That copy does not touch the real service's gate or audit trail. The check re-runs while the service is up (V22-08 fixed), but it should verify the service uid against a root-owned pin before any deployment.
- **Lexical evidence and request parsing.** Every fresh set so far (IW-4 to IW-17) found new wording that the parser or evidence matcher handled wrongly on first contact, and IW-4, IW-5, IW-6, IW-8, IW-9, IW-10, IW-11, IW-12, IW-13, IW-14, IW-15, IW-16 and IW-17 each had unsafe results from it. Since V2.7 the product identity fails closed: a name word or code next to the model ("EQ", "LTE", "Lite") must be in the candidate's identity, and a page about a coded sibling never counts for the base model. Since V2.8 a code after the model is kept even when it is a descriptor elsewhere ("HD"), and the product noun after the model ("MD-7 Headphones") must be what the listing is. Since V2.9 there is no suffix list at all: the words right after the model code are compared across sibling listings, every name word the user wrote after the code must be in the listing, a listing that carries a variant word the request did not name is another product (its offers, stored evidence and checkout identity never pass to the sibling), and a tie between named variants locks nothing. Since V2.10 the direction of "up to N" comes from the verb before it (a capacity verb makes it a minimum; with no verb only the exact value meets it). Since V2.11 a part listed under the base model is accepted only when the maker's fit statement lists the full requested model. Since V2.12 any "<thing> for the <model>" is a part request that the model itself never satisfies, and the budget is checked on quoted item, shipping and fees. Since V2.13 every product word the request writes after the model must be accounted for by the listing, a number with a unit or a minus sign next to the model is part of its identity ("Mikra 30L", "Cinder -10"), and a signed number or temperature nothing interpreted blocks. Since V2.14 a word before the product noun in a discovery request is a must-have, never background; a part phrase before "for the <model>" is kept whole; a number nothing claimed blocks; offers from a merchant whose registration is not active are never price evidence; and cm/mm next to a model are identity. Since V2.15 a checkout offer must be a listing of the locked product itself, listing titles are parsed with the request identity rules, feature evidence counts only from the product's own page, adjacent modifier words stay one requirement ("stainless steel"), and any noun phrase before "for the <model>" is a part. Since V2.16 the catalog never merges listings whose titles carry different numbers, any unit letter after a name is part of the model ("6G"), dimension strings are never the model, any "<thing> for the <model>" except a purpose is a part, and words that used to be dropped as condition or feature words ("sealed", "dishwasher") are checked or block. Since V2.17 every request word must be accounted for: a generic word that can describe the product ("water", "cooling") is never dropped, and a leftover word outside a purpose phrase is a must-have the listing title or evidence must state; any number with a unit next to a name is the model ("80lb", "12 T"); and only offers in the requested condition price the product. This is stricter, so the older seen sets lost one or two correct decisions each (more INVESTIGATE), with 0 unsafe and 0 bypasses everywhere. Each new set has still found a new form, so IW-18 should be expected to find more. The fixes are general mechanisms, but the next fresh set should be expected to find more. A statement phrased very differently from the request usually stays unverified (INVESTIGATE).
- **Context is not verified.** Since V2.5, a purpose phrase ("for my studio apartment", "for travel") is an optional CONTEXT row, never a blocking requirement. Since V2.6, a leftover word that no requirement pattern claimed is context too, unless it is negated, a comma item of its own, after a feature verb, next to another content word, model-like, or in a non-English request. A requirement phrased in a way none of these catch is therefore not checked. That is the trade made for fewer false INVESTIGATE results. IW-8 tested loose requirements and found no unsafe result from them (they stayed must-haves and gave INVESTIGATE).
- **Pooled evidence.** Since V2.6, every search result of a request is read for every candidate, and a brand-wide search is used when the budget cannot reach every model. Attribution rules are unchanged (IW-7: 0 misattributed on V2.5), but the pooled read is new and has only been measured on seen sets.
- **Nothing is deployed.** There is no remote host connector, no live PayPal, and no real merchant checkout.
